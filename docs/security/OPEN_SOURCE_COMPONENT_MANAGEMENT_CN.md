# 开源组件安全管理与漏洞处置制度

> For the English version, see [OPEN_SOURCE_COMPONENT_MANAGEMENT.md](OPEN_SOURCE_COMPONENT_MANAGEMENT.md)。

本文档说明 PikiwiDB(Pika)项目对所引入的第三方开源组件如何进行软件成分分析
(SCA)扫描、如何对扫描发现的漏洞进行分级,以及当发现**高危及以上**开源组件
漏洞时的具体处置流程、时限与责任分工,并附真实处置示例。

本制度与项目整体安全策略配套使用,漏洞上报与响应流程见 [../../SECURITY_CN.md](../../SECURITY_CN.md)。

---

## 1. 适用范围

本制度适用于 PikiwiDB 主仓库及配套工具中引入的全部第三方开源组件,包括但不限于:

- 通过 CMake `ExternalProject_Add` 在构建期拉取的 C/C++ 组件;
- 通过 Git 子模块引入的组件;
- 通过 Go module(`gomod`)引入的工具链依赖;
- CI/CD 流程中使用的 GitHub Actions 等第三方动作。

当前主要第三方组件示例(随版本演进更新):

| 组件 | 用途 | 当前版本 |
|------|------|----------|
| RocksDB | 底层持久化存储引擎 | v8.7.3 |
| protobuf | 序列化 | v3.17.3 |
| zstd / lz4 / snappy / zlib / bz2 | 压缩 | v1.5.4 / v1.9.4 / 1.1.7 / v1.3.1 |
| gflags / glog | 命令行参数与日志 | v2.2.2 / v0.6.0 |
| fmt | 格式化 | 10.2.1 |
| jemalloc / gperftools | 内存分配 | 5.3.0 |
| hiredis | Redis 客户端 | v1.2.0 |
| gtest | 单元测试 | - |

> 完整、权威的组件清单以每次发布随附的 **SBOM(软件物料清单)** 为准。

## 2. 扫描工具与频率

项目使用软件成分分析(SCA)工具对全量代码及其第三方依赖进行开源组件与已知漏洞
检测,采用的工具包括:

- **七彩棱镜**(开源组件与合规扫描)
- **墨菲 / MurphySec**(开源组件漏洞与许可证检测)
- **链图 / ChainGraph**(依赖关系与供应链风险扫描)

扫描触发时机:

| 时机 | 说明 |
|------|------|
| 版本发布前 | 每个正式版本发布前必须执行全量 SCA 扫描,并留存扫描报告 |
| 定期扫描 | 至少每月对主维护分支执行一次全量扫描 |
| 依赖变更时 | 引入新组件或升级组件版本的 PR,须触发针对性扫描 |
| 情报驱动 | 当上游披露重大漏洞(如 CVE)时,立即对受影响组件进行排查 |

此外,仓库已启用 GitHub `CodeQL`(静态安全分析)与 `Dependabot`(依赖更新提醒)
作为持续的自动化补充。

## 3. 漏洞分级标准

对 SCA 扫描发现的开源组件漏洞,统一依据国家标准
**GB/T 30279-2020《信息安全技术 网络安全漏洞分类分级指南》** 进行分级,分为四级。
对可利用性判定时,同时参考组件在 PikiwiDB 中的**实际调用情况与暴露面**
(可达性分析),以避免对不可达代码路径的误判。

| 等级 | 判定说明 | 是否阻断发布 |
|------|----------|--------------|
| 超危 | 组件漏洞可被远程、无需认证利用,且相关代码在 PikiwiDB 中可达,可能导致远程代码执行、数据大规模泄露或集群失陷 | 阻断,必须先处置 |
| 高危 | 可导致数据泄露、权限提升或服务不可用;或超危漏洞但触发条件受限 | 阻断,必须先处置 |
| 中危 | 需特定条件或已认证才能触发,影响有限 | 不阻断,限期处置 |
| 低危 | 影响轻微,利用条件苛刻,或相关代码路径不可达 | 不阻断,可随常规版本处置 |

## 4. 高危及以上组件漏洞处置流程

当 SCA 扫描发现**高危或超危**开源组件漏洞时,执行以下闭环流程:

### 4.1 处置总原则

**高危及以上漏洞未处置完成前,相关版本不予发布(release blocker)。**

### 4.2 处置步骤

1. **登记与定级**
   - 将漏洞录入项目缺陷/安全跟踪系统,标注组件名、版本、CVE 编号、SCA 工具来源;
   - 依据第 3 节标准定级,并做可达性分析确认在 PikiwiDB 中是否真实可利用。

2. **影响面分析**
   - 确认受影响的组件版本、被哪些模块引用、影响哪些已发布版本分支
     (如 `4.0` / `3.5`);
   - 判断是否已有官方修复版本或补丁。

3. **选择处置方案**(按优先级)

   | 优先级 | 方案 | 适用场景 |
   |--------|------|----------|
   | 1 | **升级组件**至已修复的安全版本 | 上游已发布修复版本,且兼容 |
   | 2 | **打补丁 / backport 修复** | 上游已修复但升级不兼容,回合关键补丁 |
   | 3 | **配置缓解 / 关闭受影响功能** | 短期内无法升级,通过配置或编译选项规避 |
   | 4 | **替换组件** | 组件已停止维护且无修复 |
   | 5 | **风险接受(仅限不可达/低实际风险)** | 经可达性分析确认不可利用,须书面记录理由并经 Maintainer 批准 |

4. **修复与验证**
   - 以 PR 形式提交修复,PR 描述关联漏洞登记编号与 CVE;
   - 通过完整 CI(编译、集成测试、`CodeQL`);
   - 重新运行 SCA 扫描,确认该漏洞已消除、且未引入新的高危项。

5. **发布与披露**
   - 视严重程度决定是否发布补丁版本/小版本;
   - 在发布说明(Release Notes / CHANGELOG)中记录:受影响组件、CVE、修复方式、
     升级后的版本;
   - 涉及对用户有安全影响的,按 [SECURITY_CN.md](../../SECURITY_CN.md) 的披露流程
     发布安全公告。

6. **归档**
   - 保存 SCA 扫描报告(处置前 + 处置后)、漏洞登记记录、修复 PR 链接,形成可审计
     的处置证据链。

### 4.3 处置时限(SLA)

| 等级 | 目标处置时限(自确认之日起) |
|------|------------------------------|
| 超危 | 7 天内完成修复或有效缓解 |
| 高危 | 30 天内完成修复或有效缓解 |
| 中危 | 90 天内处置 |
| 低危 | 随下一个常规版本处置 |

### 4.4 责任分工

| 角色 | 职责 |
|------|------|
| 安全/维护负责人 | 组织扫描、确认定级、跟踪时限、决定是否阻断发布 |
| 组件 Owner / 相关模块 Maintainer | 制定并实施处置方案、提交修复 PR |
| 评审 Maintainer | 评审修复正确性与兼容性,批准合并 |
| PMC | 对"风险接受"类决策与发布放行做最终确认 |

## 5. 处置示例说明

以下为结合 PikiwiDB 实际依赖的示例,用于说明处置流程如何落地。

### 示例一:压缩库高危漏洞 → 升级处置

- **发现**:某次发布前的 SCA 扫描(墨菲)报告 `zstd 1.5.4` 存在一个高危漏洞
  (示例 CVE-XXXX-XXXX),可在解压特制数据时触发内存越界。
- **分析**:PikiwiDB 通过 RocksDB 使用 zstd 进行数据压缩,该代码路径可达,判定为
  **高危**,阻断发布。
- **处置**:优先方案为升级——将 `CMakeLists.txt` 中 zstd 拉取版本升级到官方已修复的
  安全版本;提交 PR 并关联登记编号。
- **验证**:通过 CI(编译 + 集成测试),重新运行三款 SCA 工具确认该项清零。
- **发布与归档**:在 CHANGELOG 记录"升级 zstd 至 vX.Y.Z 修复 CVE-XXXX-XXXX",
  保存处置前后扫描报告。**处置在确认后 30 天内完成,满足高危 SLA。**

### 示例二:传递依赖超危漏洞 → backport 补丁

- **发现**:链图扫描报告底层组件 `protobuf v3.17.3` 存在一个超危解析漏洞,可导致
  远程拒绝服务。
- **分析**:升级到最新大版本会破坏兼容性,判定为**超危**,阻断发布。
- **处置**:采用"打补丁 / backport"方案,将上游针对该 CVE 的关键修复回合到当前版本
  的构建中,不做破坏性升级。
- **验证 + 发布**:CI 与 SCA 复扫通过后,发布补丁版本,并按 SECURITY 流程发布安全
  公告。**在 7 天内完成,满足超危 SLA。**

### 示例三:漏洞不可达 → 风险接受(需批准与记录)

- **发现**:七彩棱镜报告某测试期组件 `gtest` 存在一个漏洞。
- **分析**:`gtest` 仅用于单元测试,不进入发布产物,相关代码在生产部署中不可达,
  实际风险极低。
- **处置**:经可达性分析,采用**风险接受**,在漏洞登记中书面记录理由,由 Maintainer
  批准;同时计划在后续常规升级中一并处理。**该决策留痕、可审计。**
